## Q1 🔴 مُعيق — ما هو endpoint رفع توكن الإشعار؟

**البند:** 0.9 / CORE-016

### ما هو معروف

```dart
// lib/app/services/push_notification_service.dart:136-140
final request = await HttpClient().postUrl(Uri.parse(url));   // url = _storage.serverUrl (الجذر)
request.write('id=${Uri.encodeComponent(id)}&notificationToken=${Uri.encodeComponent(token)}');
```

الطلب يُرسَل إلى **جذر الخادم** بلا مسار، بصيغة `application/x-www-form-urlencoded`، بحقلَي `id` و`notificationToken`.

### البحث الذي أُجري

| البحث | النطاق | النتيجة |
|---|---|---|
| `notificationToken` | `lib/**/*.dart` | **0** |
| `notificationToken` | `openapi.yaml` | **0** |
| `/devices` · `/notifications` · `/token` | `openapi.yaml` | **0** |
| `EldEndpoints` — أي ثابت مشابه | `lib/backend/http/eld_endpoints.dart` | **0** |

### ما لا يمكن فعله

**اختراع مسار = اختراع عقد خادم**، وهو ممنوع صراحة. التخمينات المرفوضة:

| التخمين | لماذا مرفوض |
|---|---|
| `/devices` | Traccar تستخدم هذا، لكن التطبيق يستخدم `/api/session` لا `/api/…` لـ Traccar — التسمية مجهولة |
| `/notification-token` | بلا أي دليل |
| `/eld/notification-token` | بلا أي دليل |

### المطلوب

> **قرار مالك المشروع:** ما هو المسار الكامل، وهل هو على **Traccar** أم على **ELD Engine**؟ وهلendpoint موجود فعلاً أم أن هذه الميزة **معطّلة أو مهجورة**؟

### الأثر على التنفيذ

| السيناريو | الإجراء |
|---|---|
| المسار معروف | EC-0.9 يصبح كاملاً — التحويل إلى `ApiClient` مع مهلة ومصادقة وتسجيل |
| **الميزة مهجورة** | **احذف `_uploadToken` كاملاً** — أفضل من إصلاح كود يرسل لطلب لا معنى له |
| غير معروف | تنفيذ الجزء الجزئي فقط (إغلاق العميل + مهلة)، وترك الباقي |

**حتى ذلك الحين، `_uploadToken` يرسل توكن FCM إلى جذر خادم الإنتاج كل مرة يُسجَّل فيها جهاز.** هذا يستحق انتباهاً مستقلاً.

## Q2 🔴 مُعيق — هل كان استثناء `/session` مقصوداً أن يعمل؟

**البند:** 0.8 / BACK-031

### ما هو معروف

```dart
// auth_interceptor.dart:64
if (options.path == EldEndpoints.session) { return super.onRequest(options, handler); }
```

لا يتحقق أبداً لأن `EldAuthBackend` يمرّر مساراً مطلقاً (`eld_auth_backend.dart:30`).

### السؤال

الاستثناء **ميت منذ إنشائه**. إمّا:
1. **كان مقصوداً** ولا يعمل منذ اليوم الأول ← الإصلاح **يغيّر سلوكاً** كان يُفترض أنه يعمل.
2. **لم يكن مقصوداً** أصلاً ← الإصلاح توهيم ضروري فقط.

### لماذا لا يمكنني الحسم

السلوك الحالي **محايد**: عند أول تسجيل دخول `session == null` ⇒ لا كوكي يُرفق ⇒ الطلب يمرّ. عند تسجيل دخول **بتحديث جلسة موجودة**، السلوك **فرق**:

| السيناريو | قبل | بعد (مع الإصلاح) |
|---|---|---|
| أول تسجيل دخول | بلا كوكي | بلا كوكي |
| تسجيل دخول وجلسة قديمة موجودة | **كوكي قديم يُرفق** | بلا كوكي |
| تسجيل خروج | — | — |

هل إرسال كوكي قديم مع طلب إنشاء جلسة **سلوك مقصود أم خطأ**؟ لا يوجد تعليق يجيب.

### المطلوب

> **قرار مالك المشروع:** هل كان intention أن يُرسَل كوكي الجلسة القديمة مع طلب إنشاء جلسة جديدة؟
> - **لا** (وهو الأرجح) ⇒ نفّذ EC-0.8.
> - **نعم** ⇒ احذف الاستثناء بالكامل بدل إصلاحه — لأنه أُضيف بنيّة معاكسة.

### ملاحظة إضافية

الملف **معدَّل في شجرة العمل**، وعليه تعليقات `P0 Stage 1` و `P0 2B-1`. قد يكون السلوك مقصوداً من عمل حديث.

## Q3 🟡 — هل يجب توحيد `app_initializer` مع `traccarNativeClientProvider`؟

**البند:** 0.6 / CORE-005

```dart
// lib/app/app_initializer.dart:65-68
trackingService = TrackingService(
  storage: localStorageService,
  tracker: TraccarNativeClientImpl(),     // ← مُنشأ مباشرة، يتخطى المزوّد
);
```

بينما:

```dart
// tracking_providers.dart:22-26
final tracker = ref.watch(traccarNativeClientProvider);   // واعي بالبيئة
```

بعد توحيد `TrackingService` (EC-0.6)، يبقى `app_initializer` يُنشئ `TraccarNativeClientImpl` مباشرة.

### السؤال

في بيئة mock، هل `app_initializer` **يجب** أن يحترم `traccarNativeClientProvider`؟

### المطلوب

> **قرار:** هل نحتاج في Phase 0 أن يصبح `app_initializer` يحترم بيئة الموك؟
>
> **توصيتي:** **لا** — خارج نطاق Phase 0 ويحمل مخاطرة إقلاع (الإقلاع يجب ألا يعتمد على مزوّد Riverpod لم يُنشأ بعد). يُسجَّل كـ Phase 1.

## Q5 🟡 — ما السلوك الصحيح لـ `MockDvirBackend.getPreviousDvir` و `review`؟

**البند:** 0.3

```dart
// mock_dvir_backend.dart:32-33, 42-43
Future<Result<RawJson>> getById(DvirId dvirId) => throw UnimplementedError('... Phase 2');
Future<Result<void>> review({...}) => throw UnimplementedError('... Phase 2');
```

EC-0.3 يصلح `list` فقط. لكن `review` — المستخدمة في `dvir_form_page.dart:509-516` — **غير منفَّذة** في الموك.

### السؤال

هلExecution EC-0.3 وحده كافٍ، أم أن `getById` و `review` تحتاج تنفيذاً لتصبح بيئة الموك صالحة للاختبار؟

### المطلوب

> **قرار:** نطاق EC-0.3 = `list` فقط (الحد الأدنى)، أم يشمل استكمال الموك؟
>
> **توصيتي:** الحد الأدنى. استكمال الموك عمل منفصل يحتاج معرفة استجابات الخادم الحقيقية.

## Q7 🟢 — ما القيمة التشخيصية للسطر 417-420 بعد الإصلاح؟
